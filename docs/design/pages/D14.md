# D14 — Создание объекта владельца

Маршрут: `/dashboard/properties/new`

Статус: дизайн-контракт до реализации.

## Продуктовая опора

- `docs/product/prd.md`, §4.1 — владелец может создавать свои объекты, управлять контактами, фото и публикацией.
- `docs/product/prd.md`, §5.2 — создание объекта является вторым шагом owner onboarding; после него владелец добавляет номер, фото, цену и занятые даты.
- `docs/product/prd.md`, §8.1 — первый объект может стать milestone приглашённого владельца, но бонус остаётся ручным решением администратора.
- `docs/product/prd.md`, §9 и §15 — форма проектируется mobile-first, остаётся коротко объяснённой и удобной для действий большим пальцем.
- `docs/product/prd.md`, §16, этап 1, и §17.1–2 — объект, номер, фото и цены входят в базовый MVP.
- `docs/product/decision-log.md`, решение от 2026-06-11 — существующая отметка referral milestone после создания объекта сохраняется без изменений.

Страница не меняет поля объекта, обязательность server validation, значения checkbox по умолчанию, загрузку фото, создание slug, referral milestone, revalidation или redirect на страницу созданного объекта.

## Аудит текущего экрана

Форма функционально полна, но композиция делает первый шаг owner onboarding тяжелее, чем он есть:

- заголовок страницы находится внутри большой рамочной карточки;
- внутри неё `OwnerPropertyFormFields` создаёт четыре самостоятельные accordion-карточки, открытые одновременно;
- блок фотографий добавляет ещё одну вложенную градиентную карточку;
- несколько уровней padding и одинаковые рамки мешают увидеть последовательность заполнения;
- contextual-текста о следующем шаге нет, хотя после submit пользователь попадает на созданный объект и продолжает настройку номеров;
- ссылка возврата вручную повторяет стили `ButtonLink`, хотя shared-примитив уже существует;
- на 320 px открытые accordion-поверхности и отдельная карточка фото заметно удлиняют форму и создают эффект `padding в padding`.

Сохраняются без изменений:

- `createOwnerProperty` и все server-side проверки;
- обязательные значения `title`, `propertyType`, `city`, `address` на сервере;
- краткое и подробное описание, контакты, время заезда/выезда, особенности и правила;
- четыре настройки публикации и сотрудничества с агентами;
- `published=true` по умолчанию, остальные текущие defaults;
- загрузка до 10 JPG, PNG, WebP или GIF не больше 5 МБ каждый;
- первое фото становится обложкой;
- query errors `validation`, `duplicate`, `photo-type`, `photo-size`, `photo-count` и общий fallback;
- создание slug, сохранение labels, загрузка фото, referral milestone;
- redirect на созданный объект с текущими success-кодами;
- auth, owner-role, subscription и RLS ограничения существующего flow.

## Проверка повторного использования

Проверены `DashboardPageNav`, `Panel`, `FormSection`, `Input`, `Textarea`, `InlineNotice`, `Button`, `ButtonLink`, `OwnerPropertyFormFields`, D07 create-композиция и property-admin widgets.

Новый shared-компонент не нужен. `DashboardPageNav`, поля, notice и кнопки используются без изменений. В `OwnerPropertyFormFields` добавляется только opt-in `create` presentation: те же поля и names выводятся плоскими секциями внутри одной form-surface. Default presentation и DOM/classes страницы редактирования `/dashboard/properties/[propertyId]` сохраняются до отдельной задачи. Локальная правая колонка относится только к этому onboarding-шагу. `docs/engineering/component-index.md` не обновляется.

## Композиция

### Широкий экран

1. Компактная back-navigation и breadcrumbs остаются над содержимым.
2. Открытый заголовок без внешней карточки:
   - надзаголовок «Новый объект»;
   - H1 «Добавьте место для размещения»;
   - пояснение, что номера, цены и занятые даты настраиваются после создания.
3. Query error показывается между заголовком и формой через текущий `InlineNotice`.
4. Одна form-surface:
   - основная колонка содержит H2 «Данные объекта»;
   - четыре существующие группы полей идут последовательно и разделяются линиями без accordion-карточек;
   - фото являются последней плоской секцией основной колонки;
   - правая шалфейная зона «После создания» объясняет следующий существующий путь: добавить номера и цены, отметить занятые даты, проверить публичную страницу.
5. Footer той же поверхности содержит вторичное действие возврата и primary submit.

### Узкий экран

1. Навигация, заголовок, notice и форма идут одной колонкой.
2. Группы полей остаются открытыми и последовательными: создание не требует раскрывать четыре accordion вручную.
3. Двухколоночные пары полей складываются в один столбец.
4. Зона «После создания» следует после фото и отделяется одной линией.
5. Primary «Создать объект» идёт перед вторичной ссылкой и обе кнопки становятся полноширинными.
6. File input, длинные labels, описания и пользовательские строки остаются внутри 390 и 320 px.
7. Нижняя навигация и safe-area owner shell не меняются.

## Состояния

- пустая форма с текущими defaults checkbox;
- частично заполненная форма;
- длинные название, адрес и описания;
- выбраны одно или несколько фото;
- ошибки `validation`, `duplicate`, `photo-type`, `photo-size`, `photo-count` и общий fallback;
- browser file picker отменён;
- server action выполняется и после успеха делает существующий redirect;
- отсутствие auth-сессии или owner-доступа — существующие guards;
- экран редактирования объекта продолжает использовать default accordion presentation.

HTML-макет использует только демонстрационные поля и локальный переключатель ошибки. Он не выбирает реальные файлы, не отправляет форму, не создаёт объект и не запускает referral milestone.

## Доступность

- один H1, затем H2 формы и последовательные H3 групп;
- labels и descriptions остаются связанными с полями через shared `Input` / `Textarea`;
- checkbox остаются внутри полнотекстовых `label`;
- file input сохраняет видимую подпись, форматы и ограничения;
- путь после создания представлен упорядоченным списком;
- query error получает alert-семантику через `InlineNotice`;
- keyboard order идёт от back-navigation через поля и настройки к secondary и primary actions;
- focus-visible полностью берётся из shared primitives;
- кнопки имеют минимум 44 px на телефоне;
- пользовательские строки и file-name могут переноситься без горизонтальной прокрутки.

## Ограничения и план реализации

1. Не менять `createOwnerProperty`, mutation payload, upload helpers, redirect, referral milestone или error mapping.
2. Не добавлять draft autosave, preview, stepper, новые поля, геокодирование, карту, каталог типов или отдельную публикацию.
3. Изменить только `/dashboard/properties/new` и opt-in presentation существующего `OwnerPropertyFormFields`.
4. Не менять `/dashboard/properties/[propertyId]`, standalone room creation или agent routes.
5. Не добавлять route loading/error для страницы без отдельного data loader; текущий query feedback остаётся честным состоянием действия.
6. Проверить 1440, 390 и 320 px, отсутствие overflow, порядок фокуса, query error и неизменность default presentation формы редактирования.
