# D04 — Заявки владельца

Маршрут: `/dashboard/requests`

Статус: дизайн реализован и проверен на точном dev-сервере worktree; Figma не использовалась из-за исчерпанного лимита Starter.

Опора: `docs/product/prd.md` §§4.1, 5.2, 6, 9–11, 15–17; `docs/product/decision-log.md` — «Заявки и публичные страницы» и «Агентский контур»; `docs/design/rollout.md`; визуальный язык главной, D01 и D02.

## Задача страницы

Дать владельцу спокойный рабочий список запросов на проживание: быстро увидеть гостя, даты, номер, источник, сумму и статус, открыть полные данные и выполнить только разрешённое следующее действие. Страница не превращается в CRM и не обещает подтверждение проживания со стороны Bronly.

## Audit текущей реализации

### Данные и функции, которые сохраняются

- список заявок владельца в порядке существующего server loader;
- guest name, телефон, дата создания, объект или самостоятельный номер, номер, даты проживания, гости, количество комнат и комментарий;
- источник `owner`, `agent`, `collection` и ценовой snapshot: итог, цена в заявке, базовая цена номера;
- статусы `new`, `transferred_to_owner`, `accepted_by_owner`, `rejected`, `completed` без переименования доменной модели;
- фильтр по всем статусам с количеством заявок и фильтр по номеру;
- выбор активной заявки на desktop и подробности в существующем `BottomSheet` на mobile;
- ссылки `Позвонить` и `WhatsApp`;
- действия владельца: принять `new`/`transferred_to_owner`, отклонить незавершённую заявку, отметить `accepted_by_owner` завершённой;
- уведомление о запросе агента отметить принятую заявку завершённой;
- loading, общий empty, filter-empty и data-error состояния;
- desktop sidebar, mobile bottom navigation и role/auth guards shell.

Текущая D04 не содержит поиска или сортировки. Они не добавляются: это было бы расширением поведения, а задача требует сохранить существующую бизнес-логику и функции.

### Проблемы текущей композиции

- page-level `Panel` создаёт внешнюю карточку вокруг всей рабочей области;
- каждая заявка находится в отдельном `Panel`, а её содержимое делится ещё на два padded-блока;
- те же данные повторяются в sticky detail `Panel`, поэтому список и детали конкурируют по визуальному весу;
- 11 полей деталей представлены сеткой одинаковых мини-карточек с собственным фоном и padding — фактически «таблица внутри таблицы»;
- действия статуса продублированы в каждой строке и в detail pane, из-за чего первичный список перегружен кнопками;
- `Tabs` добавляет свой внешний margin внутри уже размеченного gap-контейнера;
- общий empty state теряет постоянный page header и выглядит как случайная вложенная панель;
- на узком экране шесть status tabs требуют длинного горизонтального скролла, хотя нативный select понятнее и компактнее.

## Композиция

### Desktop, 1440 px

- открытый header без внешней карточки: eyebrow `ЗАПРОСЫ НА ПРОЖИВАНИЕ`, крупный `Заявки`, описание и спокойный счётчик всех заявок;
- один toolbar: status tabs со всеми существующими статусами и счётчиками плюс select номера;
- master/detail сетка `список + 360 px`;
- список — одна кремовая поверхность, строки разделены тонкими линиями, а не самостоятельными карточками;
- строка показывает гостя, телефон, статус, даты, объект/номер, источник и итоговую сумму; клик выбирает строку;
- detail pane — одна кремовая поверхность с контактами и доступным status action;
- подробности сгруппированы в плоские строки `dt/dd` с разделителями: размещение, проживание, стоимость, комментарий. Внутренних карточек нет;
- phone/WhatsApp и мутации находятся только в деталях, поэтому не повторяются в каждой строке.

### Mobile, 390 и 320 px

- sidebar скрыт, штатная bottom navigation остаётся видна и выделяет `Заявки`;
- header и счётчик складываются без отдельной панели;
- status tabs заменяются нативным select со всеми теми же значениями, рядом остаётся select номера;
- список сохраняет одну поверхность; каждая строка складывает identity, статус и три ключевые пары данных в одну колонку;
- нажатие `Подробнее` открывает существующий `BottomSheet` с полным набором данных, контактами и допустимыми действиями;
- touch targets не меньше 44 px, длинные названия и суммы переносятся внутри viewport;
- страница не имеет горизонтального overflow на 390 и 320 px.

## Визуальные правила

- Manrope, песочный фон `--reserve-color-sand-50`, кремовая поверхность `--reserve-color-cream-50`, шалфейные `--reserve-color-sage-*` и graphite-текст из главной;
- одна смысловая группа — один владелец padding;
- границы и whitespace формируют структуру; дополнительные тени и вложенные поверхности не используются;
- semantic danger/warning оттенки остаются только у соответствующих статусов и действий;
- общие `Button`, `ButtonLink`, `BottomSheet`, `InlineNotice`, `Select`, `StatusPill` и `Tabs` переиспользуются без изменения defaults;
- новые shared-компоненты и глобальные токены не нужны.

## Состояния

| Состояние | Представление |
| --- | --- |
| данные загружены | header, toolbar, плоский master/detail список |
| заявок нет | постоянный header и один открытый empty block `Пока нет заявок` |
| фильтр без результатов | один filter-empty block со сбросом фильтров |
| загрузка | skeleton повторяет header, toolbar, строки списка и detail pane |
| ошибка loader | постоянный header и один `InlineNotice` без демонстрационных данных |
| выбранная заявка | desktop row получает `aria-current`, detail pane обновляется |
| mobile details | focus trap, Escape/close и возврат focus обеспечивает `BottomSheet` |
| запрос завершён или отклонён | контакты доступны, status mutation actions не показываются |
| агент просит завершение | существующий soft notice перед action `Отметить завершенной` |

## Доступность и интеракции

- desktop tabs сохраняют `role=tab`, стрелки, Home/End и видимый focus;
- оба mobile select имеют доступные имена; фильтры не зависят только от цвета;
- каждая summary-строка — отдельная кнопка с доступным именем гостя и `aria-current` у выбранной;
- статус всегда дублируется текстом;
- phone и WhatsApp остаются реальными ссылками, внешняя ссылка сохраняет `target=_blank` и `rel=noreferrer`;
- bottom sheet сохраняет focus trap, Escape и focus restore;
- мутационные действия остаются server forms; дизайн не меняет переходы статусов и не выполняет optimistic подмену результата.

## Ограничение изменений

D04 меняет только `/dashboard/requests`, `src/widgets/requests-browser` и согласованные route states. Loader, mapper, RLS, server actions, shell, глобальные tokens и agent requests не меняются. Поскольку `RequestsBrowser` сейчас используется только этой owner page, локальная перестройка не затрагивает `/agent/dashboard/requests`.

## Демонстрационные данные макета

`D04.html` содержит только изолированные вымышленные заявки с разными источниками и статусами. Они нужны для визуальной проверки и не попадают в production data flow.

## План проверки

1. Поднять `D04.html` по HTTP, снять и просмотреть full-page кадры 1440, 390 и 320 px.
2. Проверить overflow, контраст, status/mobile filters, выбор строки, keyboard focus и mobile detail overlay в макете.
3. После внедрения поднять точный dev-сервер этого worktree, использовать доступную авторизованную UI-сессию без чтения env/cookies/tokens и без auth bypass.
4. На live `/dashboard/requests` проверить те же три viewport, console/error overlay, status/room filters, выбор и детали, sheet focus trap, navigation и read-only contact href.
5. Не запускать `Принять владельцем`, `Отклонить` или `Отметить завершенной` на реальных данных. Мутационный E2E допустим только на явно разрешённой staging fixture; иначе пометить непроверенным.
