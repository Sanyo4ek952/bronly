# D12 — Персональные приглашения владельца

Маршрут: `/dashboard/referrals`

Статус: дизайн-контракт до реализации.

## Продуктовая опора

- `docs/product/prd.md`, §4.1 — владелец может отправлять персональные приглашения.
- `docs/product/prd.md`, §5.8 — приглашение сохраняет пригласившего и ожидаемую роль, без общего каталога пользователей.
- `docs/product/prd.md`, §8.1 — бонус получает только пригласивший после целевого действия приглашённого и ручного решения администратора; подтверждённое продление составляет 10 дней.
- `docs/product/prd.md`, §9 и §15 — интерфейс mobile-first, с ясной иерархией и удобными действиями на телефоне.
- `docs/product/prd.md`, §16, этап 3, и §17.20–21 — персональные приглашения и ручное реферальное продление входят в MVP.
- `docs/product/decision-log.md`, решение от 2026-06-11 — фиксирует роли приглашения, milestone и отсутствие автоматического начисления.

Страница не меняет генерацию или срок жизни invite, регистрацию по token, milestone, очередь `pending`, число бонусных дней, решение администратора либо контексты продлеваемой подписки.

## Аудит текущего экрана

Данные и действия корректны, но композиция дробит один сценарий на несколько равнозначных поверхностей:

- H1, пояснение и tabs находятся в отдельной поднятой `Panel`, а активное приглашение — во второй;
- внутри карточки приглашения текст и ссылка помещены ещё в две рамочные поверхности с собственным padding;
- важное правило о ручном решении администратора показано отдельным notice между данными и действиями, но путь до бонуса не объяснён последовательно;
- на desktop остаётся много пустого пространства, хотя текст приглашения и готовую ссылку удобно читать рядом;
- на 320 px две вложенные рамки, notice и две кнопки создают длинную колонку и эффект `padding в padding`;
- transient-сообщение об ошибке копирования визуально не отличается от успешного сообщения;
- route-level loading и error состояния отсутствуют;
- у маршрута нет empty state по продуктовой модели: сервер получает или создаёт по одной активной ссылке для каждой роли, а при недоступности данных возвращает пользователя в кабинет.

Сохраняются без изменений:

- авторизационные redirect и проверка owner-роли через текущий layout/data flow;
- параллельный `getOrCreateReferralInvite` для owner и agent;
- начальная вкладка «Агент»;
- заголовок, описание, share message и URL из `ReferralInviteSummary`;
- native share при наличии `navigator.share`;
- fallback на копирование, копирование текста и ссылки одним действием;
- очистка transient-сообщения при отмене native share;
- keyboard-навигация `Tabs` стрелками, Home и End;
- default-композиция `/agent/dashboard/referrals` до D35.

## Проверка повторного использования

Проверены `Panel`, `Tabs`, `Button`, `InlineNotice`, `SectionHeader`, `StatusPill`, текущие `ReferralSharePanel` и `ReferralShareCard`, owner/agent referrals pages, а также композиции D09–D11.

Новый shared-компонент не нужен. В общий referral-виджет добавляется только opt-in `owner` presentation. Default presentation и его DOM/classes остаются для `/agent/dashboard/referrals`. В owner-варианте используются существующие shared-примитивы; пояснение этапов остаётся локальной разметкой виджета, потому что второго подтверждённого потребителя пока нет. `docs/engineering/component-index.md` не обновляется.

## Композиция

### Широкий экран

1. Открытый заголовок страницы:
   - надзаголовок «Рост через рекомендации»;
   - H1 «Персональные приглашения»;
   - краткое пояснение о двух готовых ссылках и ручном бонусе.
2. `Tabs` размещены под заголовком без отдельной внешней панели и переключают роль приглашённого.
3. Одна основная поверхность делится на две зоны `minmax(0, 1fr) / 340px`:
   - слева — роль, title, description и текст приглашения;
   - справа — готовая URL, основное действие «Поделиться» и вторичное «Скопировать».
4. Между зонами используется один разделитель, без `Panel` внутри `Panel`.
5. Нижняя часть той же поверхности объясняет три шага:
   - отправить персональную ссылку;
   - приглашённый выполняет milestone своей роли;
   - администратор вручную решает вопрос о продлении на 10 дней.
6. Success/error feedback появляется рядом с действиями и не сдвигает пользователя к верхней части экрана.

### Узкий экран

1. Заголовок, tabs и основная поверхность идут одной колонкой.
2. Tabs занимают доступную ширину, обе роли остаются видимы.
3. Зона ссылки следует сразу после описания и отделяется горизонтальной линией.
4. Обе кнопки становятся полноширинными и имеют высоту не менее 44 px.
5. Этапы превращаются в вертикальный список с одним владельцем padding.
6. Длинные share message и URL переносятся без горизонтального overflow на 390 и 320 px.
7. Нижняя навигация кабинета и safe-area остаются без изменений.

## Состояния

- активна роль «Агент» (начальное состояние owner-маршрута);
- активна роль «Владелец»;
- длинные имя, share message и invite URL;
- native share доступен и успешно завершён;
- native share отменён — feedback очищен;
- native share недоступен — выполняется copy fallback;
- копирование успешно;
- копирование не удалось — error feedback и ссылка остаётся доступна для ручного копирования;
- route loading;
- route error с действием «Повторить»;
- отсутствие auth-сессии — существующий redirect на `/login`;
- invite недоступен или owner-роль отсутствует — существующий redirect на `/dashboard`.

HTML-макет использует только демонстрационные данные и локальные переключатели. Он не создаёт invite, не пишет в clipboard, не вызывает native share и не меняет подписку.

## Доступность

- один H1 и последовательные H2/H3;
- tabs сохраняют `tablist`, `tab`, `aria-selected`, управление стрелками, Home и End;
- активная tab связана с видимой зоной через `aria-controls` / `aria-labelledby`;
- этапы представлены упорядоченным списком;
- transient feedback использует `aria-live="polite"`, ошибка дополнительно получает alert-семантику через `InlineNotice`;
- смысл success/error выражен текстом, а не только цветом;
- кнопки имеют минимум 44 px на телефоне и видимый `:focus-visible`;
- URL использует `overflow-wrap:anywhere`, а контейнеры имеют `min-width: 0`;
- loading state использует `aria-busy="true"`; error state содержит явное действие повтора.

## Ограничения и план реализации

1. Не менять `getOrCreateReferralInvite`, Supabase, token, intent, роли, milestone, reward queue или admin review.
2. Не добавлять историю приглашений, статусы приглашённых, контакты, каталог пользователей, отзыв invite или генерацию новой ссылки.
3. Изменить только owner-маршрут через opt-in presentation общих referral-виджетов.
4. Не менять default-композицию `/agent/dashboard/referrals` до D35.
5. Добавить route-level loading/error только как честные визуальные состояния D12.
6. Проверить 1440, 390 и 320 px, отсутствие горизонтального overflow, tabs/focus, длинный URL, success/error feedback и неизменность agent default presentation.
