# D03 — Legacy-маршрут «Номера»

Маршрут: `/dashboard/rooms`

Статус: redirect-only; самостоятельная UI-поверхность не проектируется.

Опора: `docs/product/prd.md` §§4.1, 5.2, 5.7, 8–9, 15, 17; `docs/product/decision-log.md` — «Самостоятельные номера без объекта»; `docs/design/rollout.md`; реализованный единый список `/dashboard/properties` из D02.

## Назначение маршрута

`/dashboard/rooms` — совместимая точка входа старой навигации. Она не является отдельным списком номеров: PRD и D02 уже фиксируют единый owner-инвентарь, в котором объекты и самостоятельные номера показаны вместе, но разделены на две группы.

Создание ещё одного списка на `/dashboard/rooms` дублировало бы данные и действия `/dashboard/properties`, создало бы конкурирующую информационную архитектуру и вернуло бы запрещённую задачей вложенность поверхностей. Поэтому на маршруте сохраняется только серверный redirect.

## Redirect-матрица

| Состояние инвентаря | Целевой маршрут | Причина |
| --- | --- | --- |
| нет объектов и самостоятельных номеров | `/dashboard/rooms/new` | владелец сразу попадает в существующий сценарий создания самостоятельного номера |
| есть хотя бы один самостоятельный номер | `/dashboard/rooms/[roomId]` | открывается первый самостоятельный номер в хронологически отсортированном owner-инвентаре |
| есть только объекты | `/dashboard/properties/[propertyId]/rooms` | открывается список номеров первого объекта |

Если в инвентаре одновременно есть объект и самостоятельный номер, самостоятельный номер имеет приоритет независимо от позиции в массиве. Это сохраняет текущее поведение legacy-маршрута; порядок объектов и номеров по-прежнему задаёт существующий loader `getOwnerInventory`.

## Дизайн-решение

- `D03.html` намеренно не создаётся: у маршрута нет кадра, состояния загрузки после навигации или самостоятельных интерактивных элементов, которые требовали бы визуального макета.
- Палитра, shell, карточки и responsive-композиция не меняются: после redirect пользователь видит уже существующую целевую страницу.
- Новые shared UI-компоненты и стили не нужны. Проверены существующие `DashboardShell`, D02 `PropertyInventoryBrowser` и целевые room/property pages.
- Единственная допустимая реализация — сохранить серверный redirect до рендера UI и сделать выбор цели явно тестируемым.

## Состояния и ограничения

- Auth и owner-role guard остаются в `src/app/dashboard/layout.tsx` и выполняются раньше страницы.
- Loader, RLS, сортировка, бизнес-данные и мутации не меняются.
- Ошибки внешнего data source не маскируются новым экраном или демонстрационными данными.
- Проверка не создаёт и не изменяет production-данные.
- Адаптивность, keyboard focus и доступные состояния оцениваются на фактической целевой странице после redirect; сам redirect не добавляет focusable UI.

## План проверки

1. Unit-тестом подтвердить empty, standalone-priority и property-only ветви.
2. На точном локальном dev-сервере открыть `/dashboard/rooms` и подтвердить HTTP/browser redirect фактического owner-инвентаря.
3. Проверить конечную страницу при 1440, 390 и 320 px: отсутствие horizontal overflow и error overlay, корректный shell, клавиатурный focus и рабочую навигацию без мутаций.
4. Отдельно обозначить ветви, которые нельзя безопасно воспроизвести на live-данных без создания или удаления инвентаря.

## Результаты проверки

Проверка выполнена 2026-09-15 на точном dev-сервере ветки `http://localhost:3013` через webpack. Использованы существующий локальный env и авторизованная UI-сессия; значения env, cookies, токены и сохранённые поля не читались.

### Redirect и состояния

- Авторизованный запрос `GET /dashboard/rooms` вернул серверный `307` и открыл `/dashboard/rooms/[roomId]` первого самостоятельного номера. Это подтверждает live-ветвь `standalone-priority` на фактическом смешанном инвентаре владельца.
- Неавторизованный запрос на тот же маршрут перенаправляется layout guard на `/login`; owner-role guard не обходился.
- Empty и property-only состояния нельзя безопасно воспроизвести на текущих live-данных без создания, удаления или изменения инвентаря. Они проверены чистой функцией в unit-тестах вместе с приоритетом первого standalone room.
- Все три redirect target соответствуют существующим маршрутам. Новые страницы, данные и мутации не добавлены.

### Responsive и визуальный QA

Полностраничные снимки 1440 × 900, 390 × 844 и 320 × 720 просмотрены в локальном браузере и не добавлены в git.

| Проверка | 1440 px | 390 px | 320 px |
| --- | --- | --- | --- |
| `documentElement.clientWidth` | 1425 | 375 | 305 |
| `documentElement.scrollWidth` | 1425 | 375 | 305 |
| Горизонтальный overflow | нет | нет | нет |
| Error overlay | нет | нет | нет |
| Desktop sidebar | виден | скрыт | скрыт |
| Mobile navigation | скрыта | видна | видна |

На 1440 px конечная room page использует desktop shell; на 390 и 320 px контент складывается в одну колонку, а фиксированная mobile navigation остаётся доступной. Повторение fixed navigation в full-page stitching не является layout overflow.

### Клавиатура, навигация и console

- Десять последовательных `Tab` на ширине 390 px прошли через gallery controls, основные действия и mobile navigation. Все элементы соответствуют `:focus-visible`: gallery dots используют нативный outline, общие links/buttons — существующее шалфейное кольцо `4 px`.
- Read-only переход `К общему списку` открыл `/dashboard/properties`; browser Back вернул точный `/dashboard/rooms/[roomId]`.
- После отдельного reload авторизованной конечной страницы свежих console errors нет. Зафиксировано одно существующее Next.js dev-warning об LCP для hero-фотографии целевой room page; это относится к будущей D22 и не вызвано redirect D03.
- Начальная попытка `agent-browser` была недоступна, поэтому live QA выполнен через локальный browser runtime и его Playwright API. Mock QA не использовался.
