# D17 — Календарь объекта

Маршрут: `/dashboard/properties/[propertyId]/calendar`

Статус: дизайн-контракт до реализации.

## Продуктовая опора

- `docs/product/prd.md`, §4.1 — владелец управляет занятыми датами своих номеров.
- `docs/product/prd.md`, §5.2 — календарь занятости входит в основной путь настройки объекта.
- `docs/product/prd.md`, §6 — заявка и ручная занятость остаются разными сущностями; экран не подтверждает проживание автоматически.
- `docs/product/prd.md`, §9 и §15 — календарь проектируется mobile-first, а основные действия должны быть доступны на телефоне.
- `docs/product/prd.md`, §17.3 — ручное управление занятыми датами входит в текущий продуктовый baseline.

Страница не меняет загрузку объекта, проверку владельца, календарные server actions, payload форм, overlap validation, query feedback или модель `room_busy_ranges`.

## Аудит текущего экрана

Рабочий `OwnerCalendarBrowser` уже содержит полноценную интерактивную сетку, переключение месяца, выбор номера, создание, изменение и удаление диапазона. Проблема находится в page-level композиции:

- экран не продолжает identity-header D15/D16 и почти не показывает контекст объекта;
- название календаря повторяется в двух соседних тяжёлых карточках;
- навигация объекта визуально смешана с вводным текстом;
- до сетки нет быстрой сводки по номерам и занятым диапазонам;
- пустое состояние не даёт владельцу явного следующего шага;
- две вложенные крупные поверхности создают лишнюю рамку вокруг уже самостоятельного календарного shell.

Сохраняются без изменений:

- `getOwnerPropertyDetail`, `notFound` и owner/RLS ограничения;
- `getCalendarNotice` и query success/error;
- `OwnerCalendarBrowser`, его состояния и текущая интерактивность;
- создание, изменение и удаление занятых диапазонов;
- переключение месяца, timeline window и выбор номера;
- тексты о ручном управлении занятостью без автоматического подтверждения заявки.

## Проверка повторного использования

Проверены `AdminPageHeader`, `Panel`, `PropertySectionNav`, `ObjectStats`, `StatusBadge`, `InlineNotice`, `ButtonLink`, `OwnerDashboardCalendar`, `OwnerCalendarBrowser` и `RoomDetailPage`.

`OwnerDashboardCalendar` предназначен для сводного календаря всего owner-инвентаря и ведёт в detail-маршруты; он не заменяет редактируемую сетку одного объекта. `RoomDetailPage` — detail-композиция номера. Каноническим рабочим блоком остаётся существующий `OwnerCalendarBrowser`.

Новый компонент или глобальный стиль не требуется. Экран собирается из существующих primitives и widgets; `docs/engineering/component-index.md` не обновляется.

## Композиция

### Широкий экран

1. Back-navigation и breadcrumbs связывают календарь с общим списком и обзором объекта.
2. Открытый header продолжает D15/D16:
   - надзаголовок «Объект владельца» и текущий статус;
   - H1 «Календарь объекта»;
   - название, тип и адрес объекта.
3. Query notice располагается сразу после header.
4. Навигация «Обзор / Номера / Календарь» остаётся отдельной спокойной полосой.
5. Компактная сводка показывает существующие данные: все номера, номера с занятыми датами и число диапазонов.
6. Короткий section intro объясняет ручной характер занятости, после него без дополнительной внешней рамки расположен `OwnerCalendarBrowser`.
7. При отсутствии номеров экран показывает самостоятельное пустое состояние с переходом к созданию номера.

### Узкий экран

1. Header, статус и описание переносятся без выхода за 320 px.
2. Навигация прокручивается только внутри строки.
3. Три показателя остаются компактной строкой.
4. Intro не дублирует заголовок внутри календарной сетки.
5. Управление месяцем, горизонтальная сетка и редактор диапазона сохраняют существующее mobile-поведение `OwnerCalendarBrowser`.
6. В пустом состоянии CTA занимает доступную ширину и остаётся доступным большим пальцем.

## Состояния

- объект опубликован, скрыт или заморожен;
- несколько номеров с разными занятыми диапазонами;
- номера без занятых дат;
- объект без номеров;
- query success и error notice;
- длинное название объекта, типа и адреса;
- создание нового диапазона;
- редактирование и удаление существующего диапазона;
- overlap error и локальное уведомление календаря.

HTML-макет использует демонстрационные данные. Его элементы не создают, не изменяют и не удаляют занятые даты.

## Доступность

- один H1 и последовательные H2/H3 внутри календаря;
- статус объекта остаётся текстом, а не только цветом;
- сводка имеет доступное имя;
- текущая вкладка сохраняет `aria-current` существующего `ObjectTabs`;
- кнопки дней, диапазонов и переключения месяца сохраняют текущие accessible names;
- query error остаётся alert через `InlineNotice`;
- пользовательские строки безопасно переносятся;
- горизонтальная прокрутка ограничена календарной областью, а не документом.

## Ограничения и план реализации

1. Не менять data loader, server actions, payload, validation, redirect, storage, RLS или модель календаря.
2. Не связывать заявку с занятым диапазоном автоматически.
3. Не добавлять drag-and-drop, bulk actions, синхронизацию с внешними площадками или автоматическое подтверждение.
4. Не изменять `OwnerCalendarBrowser` и default presentation shared primitives без отдельной необходимости.
5. Изменить только page-level композицию `/dashboard/properties/[propertyId]/calendar`.
6. Проверить 1440, 390 и 320 px, отсутствие document overflow, длинные строки, пустое состояние и notices.

## Результат адаптивного QA макета

- `1440 × 900`: sidebar, identity-header, навигация, сводка, intro и календарная сетка образуют одну иерархию; внешнего горизонтального overflow не видно.
- `390 × 844`: identity и адрес переносятся, вкладки остаются в собственной прокручиваемой строке, сводка сохраняет три компактных столбца, управление месяцем складывается над календарём.
- `320 × 720`: заголовок и описание остаются читаемыми; подписи сводки допускают безопасный перенос; календарная сетка прокручивается внутри своей области, не меняя page-level ширину.
- Длинные строки и min-content поведение дополнительно защищены `min-width: 0`, `max-width: 100%` и `overflow-wrap` в статическом макете.

Скриншоты трёх размеров просмотрены вручную. Макет не открывал приложение и не выполнял server actions.
