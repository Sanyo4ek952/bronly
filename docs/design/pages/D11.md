# D11 — Уведомления владельца

Маршрут: `/dashboard/notifications`

Статус: дизайн-контракт до реализации.

## Продуктовая опора

- `docs/product/prd.md`, §4.1 — владелец получает уведомления и управляет своим кабинетом.
- `docs/product/prd.md`, §9 — интерфейс mobile-first; PWA push входит в MVP.
- `docs/product/prd.md`, §10 — поддерживаются Telegram, in-app и PWA push; события охватывают заявки, предложения агентов и подписку.
- `docs/product/prd.md`, §13.5 — `notification_settings`, `push_subscriptions`, `in_app_notifications` и `notification_deliveries` остаются существующими сущностями.
- `docs/product/prd.md`, §15 — рабочая иерархия должна быть ясной, а действия — удобными на телефоне.
- `docs/product/prd.md`, §17.16 — Telegram, in-app и PWA push являются критериями готовности MVP.

Страница не меняет состав событий, каналы доставки, сортировку, лимит выдачи, правила read/unread, адреса переходов или push-бизнес-логику.

## Аудит текущего экрана

Текущий экран функционально полон, но визуально дробит один рабочий поток:

- настройка push показана первой и получает тот же визуальный вес, что вся лента событий;
- `NotificationsCenter` — большая `Panel`, внутри которой каждая запись является ещё одной `Panel`;
- на каждой записи повторяются рамка, скругление и padding, поэтому список воспринимается как стопка самостоятельных карточек, а не хронологическая лента;
- кнопки перехода и отметки прочитанным разнесены по краям карточки и на 320 px создают длинную вертикальную композицию;
- заголовок страницы находится внутри ленты, а push-настройка выглядит как отдельный экран без общего H1;
- empty state вложен в панель и добавляет ещё одну рамочную поверхность;
- отдельные route-level loading и error состояния отсутствуют, хотя запросы уведомлений и push-статуса могут завершиться ошибкой.

Сохраняются без изменений:

- параллельная загрузка `getMyNotifications()` и `getMyPushSubscriptionStatus()`;
- сортировка: непрочитанные выше прочитанных, затем по дате;
- максимум 50 уведомлений;
- title, description, createdAt, read status, link path и link label каждой записи;
- действия «Отметить прочитанным» и «Отметить все прочитанными»;
- повторная валидация layout и маршрута после успешного действия;
- push-состояния unsupported, denied, inactive, active, saved-on-another-device и `foundation_only`;
- включение/отключение push только для текущего устройства;
- текущие success/warning сообщения и pending-состояние кнопки;
- agent-маршрут и его default-композиция до D33.

## Проверка повторного использования

Проверены `Panel`, `Button`, `ButtonLink`, `SubmitButton`, `InlineNotice`, `StatusPill`, `SectionHeader`, owner/agent страницы уведомлений, текущие `NotificationsCenter` и `PushNotificationsCard`, а также композиции D01–D10.

Новый shared-компонент не нужен. Существующие кнопки, notice и status pill сохраняются. В два общих блока добавляется только opt-in owner presentation, как уже сделано для D10: default presentation не меняется и продолжает обслуживать `/agent/dashboard/notifications` до D33. Локальная page-композиция отвечает только за заголовок и desktop-сетку.

## Композиция

### Широкий экран

1. Открытый заголовок страницы:
   - надзаголовок «События кабинета»;
   - H1 «Уведомления»;
   - короткое объяснение про заявки, предложения агентов и подписку.
2. Две колонки `minmax(0, 1fr) / 320px`:
   - основная колонка — лента in-app событий;
   - боковая колонка — одна компактная панель push для текущего устройства.
3. Заголовок ленты показывает текстовый счётчик непрочитанных. Если непрочитанные есть, рядом доступно действие «Отметить все прочитанными».
4. События лежат в одной общей поверхности и разделяются линиями:
   - непрочитанное событие получает спокойный шалфейный фон и маркер «Новое»;
   - прочитанное остаётся на кремовом фоне и получает текстовый статус;
   - время находится в правой части строки;
   - действия расположены под содержимым и не создают вложенную карточку.
5. Empty state занимает ту же поверхность ленты без дополнительной рамки.

### Узкий экран

1. Заголовок остаётся первым.
2. Лента событий идёт перед настройкой push, потому что чтение событий — основная задача маршрута.
3. Заголовок ленты, счётчик и массовое действие складываются в один поток.
4. В каждой записи время переносится под заголовок; действия занимают удобную ширину.
5. На 320 px кнопки становятся полноширинными, длинные заголовки и описания переносятся без overflow.
6. Push-панель идёт после ленты и не конкурирует с уведомлениями.
7. Нижняя навигация кабинета и safe-area остаются без изменений.

## Состояния

- несколько непрочитанных и прочитанных уведомлений;
- только прочитанные уведомления;
- пустая лента;
- pending отдельной отметки и массовой отметки;
- уведомление без ссылки;
- длинный title/description/link label;
- push не поддерживается браузером;
- permission `denied`, `default` или `granted`;
- push активен на текущем устройстве;
- у аккаунта есть подписка другого устройства;
- `foundation_only` без серверных VAPID-ключей;
- success/warning сообщение после push-действия;
- загрузка маршрута;
- ошибка загрузки с повтором.

HTML-макет использует только демонстрационные данные и локальные переключатели состояний. Он не вызывает API, не меняет уведомления и не запрашивает разрешение браузера.

## Доступность

- один H1 и последовательные H2;
- лента размечена списком, каждая запись — `article`;
- время передаётся элементом `time` с `dateTime`;
- read/unread выражается текстом, а не только фоном;
- у массового действия понятная подпись и pending label;
- transient push-сообщение использует `aria-live="polite"`;
- route error показывает явное действие «Повторить»;
- loading state имеет `aria-busy="true"` и содержательный label;
- все интерактивные элементы имеют минимум 44 px на телефоне и видимый `:focus-visible`;
- длинные строки используют перенос и не создают горизонтальную прокрутку.

## Ограничения и план реализации

1. Не менять запросы, сортировку, лимит 50, мутации, API push, service worker, VAPID или revalidation.
2. Не добавлять фильтры, удаление, пагинацию, категории, настройки Telegram или новые типы событий.
3. Изменить только `/dashboard/notifications` через opt-in owner presentation общих блоков.
4. Не менять default-композицию `/agent/dashboard/notifications` до D33.
5. Добавить route-level loading/error как визуальные состояния D11 без подмены ошибок пустым списком.
6. Проверить 1440, 390 и 320 px, отсутствие горизонтального overflow, длинные строки, focus и читаемость read/unread.
