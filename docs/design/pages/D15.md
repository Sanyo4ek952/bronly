# D15 — Обзор и редактирование объекта владельца

Маршрут: `/dashboard/properties/[propertyId]`

Статус: дизайн-контракт до реализации.

## Продуктовая опора

- `docs/product/prd.md`, §4.1 — владелец управляет своими объектами, номерами, фото, контактами и публикацией.
- `docs/product/prd.md`, §5.2 — после создания объекта владелец добавляет номер, цену, фото, занятые даты и проверяет публичную ссылку.
- `docs/product/prd.md`, §5.5 — настройки сотрудничества с агентами остаются частью объекта и не расширяют права агента.
- `docs/product/prd.md`, §7 — цены относятся к номерам и не переносятся в форму объекта.
- `docs/product/prd.md`, §9 и §15 — экран остаётся mobile-first, читаемым и удобным для основных действий большим пальцем.
- `docs/product/prd.md`, §16, этапы 1–2, и §17.1–3 — объект, номера, фото, цены и занятые даты составляют основной owner-flow.

Страница не меняет поля объекта, server actions, проверки владельца, загрузку и порядок фото, удаление, публикацию, заморозку, настройки сотрудничества, redirect или query feedback.

## Аудит текущего экрана

Текущий экран функционально полный, но визуально конкурирует сам с собой:

- рамочный header, крупная карточка объекта и карточка редактирования имеют одинаковый вес;
- на телефоне полноразмерная карточка с обложкой, повторяющимися ссылками и кнопками отодвигает форму далеко вниз;
- локальные tabs смешивают маршруты объекта с якорями «Контакты» и «Фото», хотя соседние страницы используют канонические разделы «Обзор / Номера / Календарь»;
- desktop aside повторяет зону удаления, хотя полноценное подтверждение уже находится в основном потоке;
- одинаковые действия на номера, календарь и публичную страницу повторяются текстовыми ссылками и кнопками;
- sticky actions появляются только после длинных блоков и не считываются как завершение формы.

Сохраняются без изменений:

- `getOwnerPropertyDetail`, `notFound` и owner/RLS ограничения;
- `updateOwnerProperty` и все имена полей `OwnerPropertyFormFields`;
- `uploadPropertyPhoto`, `setPropertyPhotoPrimary`, `deletePropertyPhoto`;
- `deleteOwnerProperty` и подтверждение точным значением `DELETE`;
- query notices и существующее различие success/error;
- статусы опубликован / скрыт / заморожен;
- счётчики номеров, активных номеров и занятых диапазонов;
- public URL владельца и переход в настройки профиля, если публичной ссылки ещё нет;
- все переходы на номера, календарь и публичную страницу.

## Проверка повторного использования

Проверены `DashboardPageNav`, `AdminPageHeader`, `AdminPageLayout`, `PropertySectionNav`, `ObjectSummaryCard`, `ObjectStats`, `StatusBadge`, `PhotoManager`, `DangerZone`, `StickyActions`, `InlineNotice`, `Button`, `ButtonLink` и `OwnerPropertyFormFields`.

Новый компонент или новый глобальный стиль не требуется. Экран собирается из существующих primitives и property-admin widgets. Каноническая `PropertySectionNav` заменяет локальный массив из пяти tabs. Desktop сохраняет `ObjectSummaryCard`, а мобильная сводка использует существующие `ObjectStats` и `StatusBadge` без тяжёлой обложки. Для `ObjectStats` добавляется только opt-in `stackOnMobile=false`; default-поведение остальных экранов сохраняется. `docs/engineering/component-index.md` не обновляется.

## Композиция

### Широкий экран

1. Back-navigation и breadcrumbs остаются первыми.
2. Открытый header без внешней карточки:
   - надзаголовок «Объект владельца» и текущий статус;
   - H1 с названием объекта;
   - тип, город и адрес;
   - копирование ссылки и открытие публичной страницы либо переход в настройки профиля.
3. Query notice следует сразу под header и получает отдельное визуальное место.
4. Каноническая навигация «Обзор / Номера / Календарь» расположена в спокойной полосе.
5. Двухколоночная рабочая область:
   - слева — редактирование, фото, удаление и sticky actions;
   - справа — существующая карточка объекта с обложкой, статистикой и быстрыми переходами;
   - повторная компактная зона удаления из aside убирается.
6. Редактирование сохраняет accordion-секции: на повторном посещении владелец может открыть только нужную группу.

### Узкий экран

1. Header, actions и notice складываются в одну колонку; кнопки не выходят за 320 px.
2. Вместо крупной карточки с обложкой показывается компактная сводка со статусом и тремя существующими метриками.
3. Быстрые переходы «Номера», «Календарь» и публичная страница доступны до формы.
4. Навигация остаётся горизонтально прокручиваемой без overflow страницы.
5. Accordion-поля, фото и зона удаления идут одним потоком.
6. Sticky actions остаются над нижней навигацией owner shell и становятся полноширинными.

## Состояния

- опубликованный, скрытый и замороженный объект;
- объект с публичной ссылкой и без неё;
- объект без номеров, без фото, без контактов или без правил;
- объект с длинным названием, адресом и пользовательскими описаниями;
- query success и error notice;
- фото отсутствуют, загружаются, становятся обложкой или удаляются;
- сохранение формы;
- неверное и верное подтверждение `DELETE`;
- отсутствующий или недоступный объект приводит к текущему `notFound`.

HTML-макет использует демонстрационные данные. Его кнопки не сохраняют объект, не загружают фото, не меняют публикацию и не удаляют данные.

## Доступность

- один H1 и последовательные H2/H3;
- текущий статус остаётся текстом, а не только цветом;
- navigation имеет понятную подпись и корректный active state;
- actions используют shared focus-visible состояния;
- все поля сохраняют labels и descriptions текущих shared primitives;
- query error остаётся alert через `InlineNotice`;
- confirmation input находится рядом с объяснением необратимого действия;
- пользовательские строки переносятся, а горизонтальная прокрутка ограничена только строкой навигации;
- touch targets основных действий не меньше 44 px на телефоне.

## Ограничения и план реализации

1. Не менять data loader, server actions, payload, validation, revalidation, redirect, storage или RLS.
2. Не добавлять autosave, preview mode, аналитику, новые поля, карту, новые статусы или управление ценой объекта.
3. Изменить только композицию `/dashboard/properties/[propertyId]` и использовать существующие компоненты.
4. Не менять страницы номеров и календаря: для них будут отдельные последовательные задачи.
5. Не менять default presentation `OwnerPropertyFormFields`.
6. Проверить 1440, 390 и 320 px, отсутствие overflow, query notice, вариант без public slug и порядок мобильных действий.
