# Готовность Bronly к следующему этапу

Снимок аудита: 2026-09-15.

## Продуктовая опора

План не вводит новых продуктовых решений и опирается на:

- PRD 12 — стек приложения;
- PRD 14 — Supabase и RLS;
- PRD 17 — критерии готовности MVP;
- `docs/product/decision-log.md` — стабильная ссылка агента, самостоятельные номера и ручное реферальное продление.

Все улучшения из PRD 19 остаются за отдельным продуктовым решением и не входят в этот план автоматически.

## Главные разрывы до выпуска

1. Рабочее дерево содержит крупную незакоммиченную переработку. До публикации нужен единый проверяемый checkpoint и осмысленный review diff.
2. Связанный Supabase-проект содержит миграции только до `202606120001`. Семь локальных миграций еще не применены:
   - `202609140001_align_calendar_pricing_boundaries.sql`;
   - `202609140002_harden_data_access.sql`;
   - `202609150001_subscription_enforcement.sql`;
   - `202609150002_agent_workflow_hardening.sql`;
   - `202609150003_collections_hardening.sql`;
   - `202609150004_notifications_pwa_hardening.sql`;
   - `202609150005_referrals_admin_hardening.sql`.
3. Код и удаленная схема поэтому пока несовместимы для полноценного релиза: новые ограничения, RPC, RLS, коллекции, доставка уведомлений и реферальная модерация отсутствуют в связанной базе.
4. VAPID и Telegram-переменные отсутствуют в локальном окружении. Это не ломает in-app уведомления, но оставляет внешние каналы в `pending_configuration`; состояние production-переменных нужно проверить отдельно без вывода секретов.
5. Unit- и SQL-smoke покрытие есть, но автоматического браузерного E2E-контура в репозитории нет. Ручные browser smoke из истории не защищают будущие изменения на каждом pull request.

## Поэтапная реализация

### Этап 1. Автоматический контроль кода

Статус: реализован этим аудитом.

- GitHub Actions запускает установку зависимостей, encoding-check, `git diff --check`, ESLint, 98 unit-тестов, TypeScript и production build.
- Workflow не использует production-секреты и проверяет fail-closed сборку.

Критерий выхода: workflow успешно проходит на ветке с полной переработкой.

### Этап 2. Staging-база и миграции

Статус: следующий обязательный этап.

1. Создать отдельный Supabase staging-проект или подтвержденную копию production-схемы.
2. Применить к staging семь новых миграций в порядке имен файлов.
3. Запустить пять транзакционных SQL smoke-тестов из `tests/rls`.
4. Перегенерировать типы через `npm run supabase:types` и убедиться, что неожиданных изменений нет.
5. Проверить миграции на копии реальных данных, особенно очистку дублей коллекций и уведомлений перед созданием unique index.

Критерий выхода: история staging совпадает с локальной, 5/5 SQL smoke проходят, данные после миграции согласованы.

### Этап 3. Автоматический E2E на staging

Статус: после этапа 2.

Добавить Playwright и изолированные тестовые аккаунты для четырех ролей. Минимальный набор:

- owner: регистрация, объект, самостоятельный номер, фото, цена, занятые даты, публичная ссылка;
- guest: фильтр, конкретный `room_id`, заявка и сохраненный ценовой snapshot;
- agent: предложение, принятие владельцем, витрина, передача заявки владельцу, запрос `completed`;
- admin: ручное продление, referral queue, скрытие страницы и блокировка объекта;
- collections: объект/номер, актуальная цена, заявка на конкретный номер и дедупликация открытия;
- PWA: manifest, service worker и подписка push при доступной browser permission.

Критерий выхода: критический happy path и основные запреты ролей проходят в CI против staging.

### Этап 4. Подготовка внешних каналов

Статус: может выполняться параллельно этапу 3.

1. Проверить `NEXT_PUBLIC_APP_URL` и Supabase Auth redirect URLs.
2. Настроить SMTP для подтверждения email.
3. Создать VAPID-пару и заполнить production-переменные.
4. Настроить Telegram bot webhook с secret token.
5. Провести реальные тестовые доставки push и Telegram, не используя пользовательские данные.

Критерий выхода: in-app, push и Telegram имеют успешные delivery-status на тестовом событии.

### Этап 5. Production rollout

Статус: требует отдельного подтверждения пользователя.

1. Зафиксировать код в отдельной release-ветке и получить зеленый CI.
2. Сделать резервную копию базы и проверить план отката.
3. Применить семь миграций к production Supabase.
4. Сразу после миграций выполнить безопасные read-only проверки схемы и RLS.
5. Развернуть соответствующую версию приложения.
6. Проверить owner, guest, agent и admin сценарии на специально созданных тестовых данных.

Критерий выхода: версия кода и история миграций совпадают, критические сценарии проходят, новые server diagnostics не появляются.

### Этап 6. Наблюдение после выпуска

Статус: после этапа 5.

- Контролировать ошибки заявок, auth callback, RPC и notification delivery.
- Проверять размер очередей `pending_configuration` и referral `pending`.
- Подтвердить резервное копирование и восстановление Supabase.
- После стабилизации собирать только метрики из PRD 18.

## Что не начинать автоматически

Онлайн-оплату проживания, общий каталог, рекомендации, отзывы, интеграции с площадками, SMS, сложный CRM и остальные пункты PRD 19 нельзя брать в реализацию без нового решения в `docs/product/decision-log.md`.
