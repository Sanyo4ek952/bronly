# Playwright E2E для ролевых сценариев

Продуктовая опора: PRD §§4–6, 8, 14 и 17; `docs/product/decision-log.md`, разделы «Роли и права», «Заявки и публичные страницы» и «Агентский контур».

## Что покрыто

- `owner`: выбор роли при регистрации, вход, кабинет, объекты, самостоятельный номер, фото, цена, календарь занятости, публичная ссылка и запрет входа в agent/admin контуры;
- `guest`: фильтр одной персональной витрины, сохранение конкретного `room_id`, отправка заявки и проверка ценового snapshot в базе;
- `agent`: выбор роли при регистрации, автоматическая публичная ссылка, предложения, сотрудничества, заявки, сделки, read-only календарь и запрет входа в owner/admin контуры;
- `admin`: очередь реферальных проверок, пользователи и скрытие страниц, подписки и ручное продление, объекты и заморозка.

Сценарии выполняются в desktop Chromium и в mobile viewport Pixel 7. Тесты проверяют доступность управляющих действий, но не нажимают необратимые admin/agent кнопки. Guest-write smoke создает одну заявку, проверяет `room_id`, источник и `pricing_snapshot`, затем удаляет запись в `finally`.

## Безопасность окружения

Мутации разрешены только при `E2E_ALLOW_MUTATIONS=true`. Preflight и тестовый helper отклоняют production-приложение `bronly-opal.vercel.app` и production Supabase project ref `uevwqievuzakcquselku`.

Нельзя использовать реальные аккаунты или пользовательские данные. Нужны отдельный staging Supabase и три тестовых аккаунта: owner, agent и admin. В staging заранее подготовьте:

1. owner-профиль с публичным slug, активной подпиской, опубликованным объектом и активным номером;
2. доступный диапазон дат и стабильный `room_id` для guest-сценария;
3. agent-профиль со стабильным `agent_public_id`;
4. admin-профиль;
5. owner-профиль и объект с уникальными именами для поиска в админке.

Скопируйте `.env.e2e.example` в `.env.e2e.local` и замените заглушки staging-значениями. Файл `.env.e2e.local` не коммитится.

## Локальный запуск

```powershell
npm run test:e2e:install
npm run test:e2e
```

Без полного набора переменных локальный запуск пропускает только неподготовленные role-suite. Строгий CI-запуск сначала проверяет все обязательные значения:

```powershell
npm run test:e2e:ci
```

Для локального `E2E_BASE_URL=http://127.0.0.1:3000` Playwright сам запускает Next.js dev server и передает ему `E2E_SUPABASE_*` как серверные переменные приложения. Для уже запущенного сервера укажите `E2E_SKIP_WEB_SERVER=true`.

## GitHub Actions

Workflow `.github/workflows/e2e.yml` запускается на `main` и вручную, когда repository variable `E2E_STAGING_ENABLED` равна `true`. Несекретные fixture identifiers сохраняются в repository variables, аккаунты и Supabase keys — только в Actions secrets. Обычный CI всегда выполняет `npm run test:e2e:list`, поэтому синтаксис и обнаружение тестов проверяются даже до подключения staging.
